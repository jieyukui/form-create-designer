## 我认为还需要考虑的问题

### 1. **作用域污染与冲突处理**
- 用户代码中可能定义了与 window 属性同名的局部变量，此时应该优先提示局部变量
- 例如：用户定义了 `const Math = {...}`，此时 `Math.` 应该优先提示用户自定义的 Math

### 2. **原型链补全**
- 当前只处理了 `对象.属性` 的直接访问，没有处理原型链上的属性
- 例如：`[].` 应该能提示 Array.prototype 上的方法（push、pop 等）
- 例如：`"".` 应该能提示 String.prototype 上的方法

### 3. **链式调用补全**
- `document.querySelector('.class').` 应该能继续提示 Element 的方法
- 这需要某种类型推断机制，复杂度较高，但可以设计一个可扩展的框架

### 4. **异步加载与缓存策略**
- 当前 `createWindowCompletionSource` 的缓存是永久的，但如果 window 属性在运行时新增（如动态加载的脚本），缓存不会更新
- 需要考虑缓存失效策略

### 5. **性能优化**
- `getWindowCompletions` 使用 `Object.getOwnPropertyNames` 扫描所有属性，这在某些环境下可能很慢
- 对于已知的内置对象，应该优先使用预定义数据，避免不必要的 window 属性扫描

### 6. **文件组织与加载**
- `builtin.js` 目前是静态导入，体积较大
- 应该支持按需加载（如只加载当前环境存在的对象）
- 可以按类别拆分：`math.js`, `dom.js`, `storage.js` 等

### 7. **环境适配**
- Node.js 环境没有 `window`、`document`、`localStorage` 等
- Web Worker 环境有不同的全局对象
- 服务端渲染（SSR）环境可能需要特殊处理

### 8. **TypeScript 类型支持**
- 当前补全信息的 `detail` 是字符串，对于复杂类型不够精确
- 考虑支持更结构化的类型信息，方便未来扩展
